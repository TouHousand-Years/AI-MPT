# 添加 Harness 音频分析内核

Parent: ../map.md  
Type: design  
Status: resolved  
Blocked by:

## 目标

为 OpenMPT for AI 增加一个独立、可替换的音频试听与评审内核。它接收
OpenMPT 生成的真实音频，允许多模态 AI 直接听音频，也保留人工试听入口，
并通过 MCP 作为工具提供给主 Agent。

首版只解决两类问题：

1. 试听一个音色，并判断它是什么类型、承担什么编曲角色，以及具有怎样的
   声音特征。
2. 试听一个乐段，并判断整体听感是否协调，指出明显问题或按约定的四个
   维度给出评审。

该内核的评审意见是证据，不是乐谱事实，也不能直接修改 Pattern。所有意见
都必须记录产生来源：`human` 或 `multimodal_ai`。

## 已确定的方案

### Harness 基底

首版使用 **PydanticAI** 作为 Python 侧 Harness 基底，在现有 MCP Sidecar
旁边运行。它负责：

- 组织试听任务生命周期；
- 适配多模态模型的文本、音频输入和结构化结果；
- 校验模型返回的评审结构；
- 管理可替换的模型提供商适配器；
- 将模型评审与 OpenMPT 文档快照、音频和范围绑定。

PydanticAI 只作为编排与校验层，不成为 OpenMPT 音频、Pattern 或 UI 的
所有者。OpenMPT 仍拥有文档、播放、离线渲染和用户编辑状态。

候选基底的取舍如下：

| 基底 | 结论 | 原因 |
| --- | --- | --- |
| PydanticAI | 首版采用 | 与 Python Sidecar 同语言，适合工具调用、模型适配和结果校验；当前需求不需要完整通用 Agent 运行时 |
| DeepSeek Harness | 暂不采用 | 更适合未来的通用 Agent 内核，但当前开发预览状态和较大的插件/运行时范围会增加集成面 |
| Pi | 暂不采用 | 工具和模型可扩展，但当前没有足够理由承担音频消息传递和适配器补全工作 |

如果后续试听内核扩展为具有长期记忆、复杂计划、工具循环和多 Agent 协作
的通用 Agent，再重新评估是否迁移 Harness；试听任务的领域接口不得依赖
PydanticAI 的内部类型。

### 模型接入策略

模型通过提供商适配器接入，内核不把任一提供商写死在 MCP 或 OpenMPT 代码
中。当前候选为：

- `qwen3.5-omni-plus`；
- Gemini 3.1 Pro Preview，对应 API 名称在实现前必须再次核实；
- Gemini 3.8 Flash，具体可用模型 ID 在实现前必须再次核实。

最终默认模型不凭名称决定，而以同一批音色和乐段的人工对照试听结果选择。
模型是否声明支持音频输入、图像输入、结构化输出和当前账号权限，必须在
适配器启动检查中验证。能力不满足时返回明确错误，不伪装成文本评审。

### 两条试听路径

#### 音色试听

音色试听复用钢琴卷帘现有的乐器试听路径，并允许传入音高；未提供时默认
使用 `C-5`。输入应包含当前文档身份、修订号、绑定 Pattern/通道或乐器
上下文，以及试听音高和时长范围。

这条路径只生成单个音色的试听音频，不要求生成完整乐段。若原有钢琴卷帘
路径只能播放而不能取得稳定的模型输入音频，则在原有播放实现外增加一个
受控的捕获/编码适配器，不能让 Sidecar 重新实现音频合成。

#### 乐段试听

乐段试听使用现有音频范围导出能力。若当前导出接口不能表达精确的 Pattern、
Order occurrence、行范围或文档修订，则补充范围导出适配器，并将导出范围
绑定到一次不可变文档快照。

默认导出完整可听混音；选中的通道是评审焦点，不应默认破坏性 solo。导出
结果必须能够追溯到：文档修订、Order/Pattern occurrence、半开区间
`[startRow, endRow)`、通道集合、采样率、声道数和编码格式。

这条路径与既有 Context Package 的 Audio Preview 概念兼容，但首版是独立
的试听工具：不要求先生成 Piano Roll 图片，也不要求 Mini Audio Reviewer
成为主 Agent 的完整上下文包。未来可以把同一份音频句柄作为 Context Package
的可选证据。

## 评审规则

### 音色分类

音色不采用互斥的单一分类，而采用可组合的三个维度。这样可以同时表达
“合成感的 Bass 弦乐垫”等实际情况。

| 维度 | 首版值示例 | 说明 |
| --- | --- | --- |
| 乐器家族 | `piano`、`strings`、`winds`、`drums_percussion`、`voice`、`guitar`、`keys`、`sfx`、`other`、`unknown` | 描述听起来像哪类乐器或声源 |
| 编曲角色 | `bass`、`lead`、`chord`、`pad`、`rhythm`、`accent`、`unknown` | 描述在编曲中的可能职责，不等同于乐器家族 |
| 声音特征 | `acoustic_like`、`synth_like`、`hybrid`、`noise_like`、`unknown` | 描述听感，不宣称真实制作来源 |

规则：

1. 音色清晰且常见时，优先直接回答易懂的乐器名称，例如“普通钢琴”；
   不强迫用户阅读完整标签对象。
2. 难以直接命名时，改为输出三个维度，并允许每个维度有多个标签、置信度
   和“不确定”说明。
3. `bass` 是编曲角色，不是乐器家族；“实录”不是仅凭听感可以可靠证明的
   声学事实。真实录制来源只能来自用户或工程元数据；AI 最多报告
   `acoustic_like` 等声音特征。
4. AI 不得从音频推断不存在的乐器、采样库、插件名称或录音来源。
5. 无法判断时明确返回 `unknown` 和理由，而不是强行选择一个标签。

建议的结构化结果形状：

```json
{
  "summary": "普通钢琴",
  "family": ["piano"],
  "roles": ["chord"],
  "character": ["acoustic_like"],
  "confidence": 0.86,
  "uncertainties": [],
  "evidence": "清晰的击弦起音和钢琴衰减特征"
}
```

### 乐段和谐性评审

评审不是简单的二元“和谐/不和谐”。它应能表示 `harmonious`、`issues_found`、
`uncertain` 三种结论，并在有依据时给出音频时间位置；如果有可用的乐谱上下文，
同时给出 Pattern 行范围。

输出规则：

1. 有明显问题时，先直接指出问题，再给出必要的证据、严重程度和时间位置。
2. 没有明显问题时，按以下四方面表述；每一方面都允许 `good`、`issue`、
   `uncertain`：
   - **音高与和声**：旋律、和弦、低音之间是否存在疑似冲突；
   - **节奏与配合**：声部是否协调，是否有不自然的错位或抢拍；
   - **音色与混音**：是否拥挤、遮蔽、刺耳、失衡或动态不足；
   - **总体听感**：结合提供的风格意图说明整体效果。
3. “东方风”等风格描述只能作为显式的评审提示输入，不能默认注入或冒充
   客观标准。
4. AI 不得把推测写成确定的乐谱事实；听感判断与 Score Context 中的源事件
   必须分开。

建议的结构化结果形状：

```json
{
  "verdict": "issues_found",
  "summary": "低音在 00:02.4 附近与和弦发生明显碰撞",
  "issues": [
    {
      "category": "pitch_harmony",
      "severity": "major",
      "startSeconds": 2.4,
      "endSeconds": 3.1,
      "description": "低音与上方和弦形成持续的疑似冲突"
    }
  ],
  "dimensions": {
    "pitch_harmony": "issue",
    "rhythm_coordination": "good",
    "timbre_mix": "uncertain",
    "overall_feel": "issue"
  },
  "uncertainties": []
}
```

模型返回的结构化字段由 Harness 校验；自然语言评论作为解释保留，不能
替代必需的来源、快照和音频绑定信息。

## MCP 能力边界

### 工具方向

至少提供以下两个面向主 Agent 的工具：

- `audition_timbre`：从当前 OpenMPT 文档生成指定音高的音色试听任务，选择
  AI 评审、人工评审或两者；默认音高为 `C-5`。
- `audition_passage`：从明确的文档范围生成乐段试听任务，选择 AI 评审、
  人工评审或两者。

由于 AI 评审和人工评审可能异步完成，工具可以先返回 `taskId`、状态、音频
句柄和快照摘要，再通过支持操作查询和提交结果。支持操作的最终名称可以在
MCP schema 阶段确定，但至少需要：

- 查询任务状态和已完成的评审结果；
- 创建/打开人工试听任务；
- 提交人工评审；
- 取消仍在运行的任务。

MCP 工具不得提供以下能力：

- 直接修改 Pattern、乐器、Sample、插件或工程设置；
- 让调用者填写 `source: human` 来伪造人工意见；
- 绕过文档修订检查、云端授权或范围限制；
- 让 AI 评审结果自动进入 Proposal 或自动 Apply。

### 请求绑定

每个试听任务都绑定以下不可变信息：

- `appInstanceId`、`documentId` 和文档 `revision`；
- 试听对象：音色或乐段；
- 规范化的 Pattern/Order/行/通道范围；
- 生成音频的 `contentHash`、格式、采样率、声道数和时长；
- 使用的系统提示词版本、主 Agent 提示词和可选风格提示；
- Harness、提供商、模型和评审 schema 版本。

文档发生任何修订后，旧任务仍可读，但其结果标记为 `stale`，不得被当作
当前文档的评审依据。系统不跟随“当前选区”自动重建旧任务。

### 评审来源

所有最终意见都使用统一的来源包络：

```json
{
  "source": "human",
  "reviewId": "...",
  "taskId": "...",
  "documentRevision": "...",
  "audioContentHash": "...",
  "createdAt": "...",
  "status": "completed",
  "result": {}
}
```

AI 来源必须额外记录提供商、模型、模型响应 ID（若有）、提示词版本和输入
哈希。人工来源必须由人工 UI 的提交动作产生，并记录提交者和提交时间；MCP
调用方不能通过参数伪造人工身份。人工意见和 AI 意见并列保存，不互相覆盖。

## 系统结构

```text
OpenMPT UI / Pattern Editor
        │
        ├─ 音色试听适配器（钢琴卷帘音符/乐器试听）
        ├─ 乐段导出适配器（范围、快照、完整混音）
        └─ 人工试听 UI（播放同一份音频并提交意见）
        │
        ▼
Application Capability / App broker
        │  文档身份、修订检查、范围规范化、任务取消
        ▼
MCP Sidecar + PydanticAI Harness
        │  任务生命周期、结果 schema、提示词合并、临时句柄
        ▼
Provider adapters
        │
        ├─ Qwen Omni
        └─ Gemini
```

边界要求：

- C++/MFC 侧拥有真实播放和离线音频生成；Python 侧不得复制 tracker 音频
  语义，也不得从文件路径自行读取工程内容。
- Application Capability 层负责在文档拥有线程捕获快照，并把范围和音频
  句柄交给 Sidecar；Sidecar 只处理协议、任务和模型调用。
- 人工 UI 播放与 AI 评审使用同一份音频内容，避免人工和 AI 实际听到不同
  的渲染结果。
- 音频、任务和评审结果默认是临时会话数据。除调试所需的输入/输出日志外，
  首版不新增项目级持久化数据库。

## 提示词与项目级 `AGENT.md`

评审提示词按以下顺序合并：

1. 系统提示词：定义安全边界、来源语义和输出 schema；
2. 主 Agent 传入的任务提示词；
3. 已保存工程中的项目级音频子 Agent `AGENT.md`，如果存在；
4. 当前试听请求的范围、风格和用户补充说明。

保存工程后，首次调用试听能力时，如果项目中缺少专属音频子 Agent 的
`AGENT.md`，可以创建它。主 Agent 可读写该文件，音频子 Agent 只读；后续
调用必须读取已有内容，不覆盖主 Agent 的修改。

未保存工程没有可靠的项目目录，因此：

- 不创建项目级 `AGENT.md`；
- 不自动改用全局文件；
- 仍允许使用系统提示词和主 Agent 提示词继续试听评审；
- 向用户明确提示：保存工程后才能启用项目级提示词。

## 任务生命周期与失败语义

一次试听任务按以下阶段运行：

1. 校验 MCP 调用、应用连接、文档身份、范围和用户授权；
2. 在文档拥有线程捕获不可变快照；
3. 通过原生路径生成音频并计算内容哈希；
4. 如果请求人工评审，发布人工试听任务；
5. 如果请求 AI 评审，检查提供商和多模态能力，提交文本与真实音频；
6. 校验结果、附加来源包络并发布完成状态；
7. 文档修订变化时标记旧结果过期，不自动重跑。

首版至少区分以下失败：

- `notAttached`：Sidecar 没有绑定有效的 OpenMPT 应用/文档；
- `documentGone` / `instanceGone`：应用或文档生命周期已结束；
- `revisionConflict`：捕获期间文档修订不一致；
- `invalidRange`：试听范围为空、越界或含义不明确；
- `renderFailed`：原生音频生成失败；
- `audioEncodingFailed`：音频无法转为提供商要求的格式；
- `providerUnavailable`：提供商、凭据或网络不可用；
- `reviewerCapabilityMismatch`：模型不支持所需的音频输入或结构化输出；
- `reviewFailed`：模型请求或结果校验失败；
- `cancelled`：用户取消任务；
- `stale`：结果对应旧文档修订。

失败不能退化成“模型没有听到音频但仍然给出意见”。错误响应可以包含安全
诊断信息，但不得泄露凭据、项目路径、无关资源或完整音频内容。

## 隐私、授权和资源限制

首次启用云端评审前，用户必须明确选择提供商并授权发送数据。授权应在 UI
中可见、可撤销，并至少覆盖：

- 有界的试听音频；
- 必要的匿名化 Score Context 或范围摘要；
- 用户明确提供的评审提示词。

默认不得发送项目路径、用户名、凭据、无关 Pattern、诊断日志或未请求的
资源。应用关闭、文档关闭或临时句柄过期后，Sidecar 不得把句柄解析到新的
“当前文档”。

首版应为音色和乐段分别设置最大时长、最大导出大小、单任务超时和取消路径；
具体数值在原生导出能力和候选模型限制核实后写入 MCP schema 与测试夹具。
这些限制只能收紧，不能由 MCP 调用者任意扩大。

## 实施阶段

### 阶段 0：冻结契约和测试夹具

- 定义音频句柄、范围、任务状态、来源包络和两类结果 schema；
- 确定错误码、修订绑定和 stale 规则；
- 准备至少一组普通钢琴、Bass、鼓、弦乐/管乐和合成音色；
- 准备至少两段已知问题不同的乐段，以及人工参考意见；
- 记录候选模型的实际 API、音频格式、时长和结构化输出能力。

阶段门：schema 可以在没有真实模型的情况下由 mock provider 完成往返，且
跨修订、取消和错误用例可确定性测试。

### 阶段 1：接通音色试听

- 从钢琴卷帘现有试听路径获得稳定音频；
- 支持可选音高和默认 `C-5`；
- 添加音频哈希、时长和快照绑定；
- 通过 mock provider 验证清晰音色直答和不确定音色三维输出；
- 增加人工播放同一音频并提交意见的最小 UI/API。

阶段门：同一音色的人工与 AI 任务可以分别完成，来源标记不可伪造，文档
修改后旧意见变为 stale。

### 阶段 2：接通乐段试听

- 复用现有音频范围导出；
- 如果不能表达准确范围，补充范围导出适配器；
- 确保使用完整混音、明确范围和文档快照；
- 验证“明显问题优先指出”和“四维度评审”两种输出路径；
- 支持音频时间位置与 Pattern 行位置的可选关联。

阶段门：同一范围可以被人工和 AI 听到同一份音频，超范围、空范围和修订
冲突都会得到 typed failure。

### 阶段 3：接入真实提供商

- 实现提供商适配器和启动能力检查；
- 统一文本、音频、可选图片/Score Context 输入；
- 记录模型、提供商、提示词版本和输入哈希；
- 在用户授权和凭据缺失时快速失败；
- 用固定夹具进行人工盲评，比较候选模型的音色分类和乐段问题定位。

阶段门：选定首版默认模型，并保留至少一个可替换适配器；提供商失败不会
污染人工结果或改变 OpenMPT 文档。

### 阶段 4：暴露 MCP tools

- 将两条试听路径接入现有本地 MCP Sidecar；
- 实现任务查询、人工提交、取消和结果读取；
- 复用现有 attach、document identity、owning-thread 和修订错误边界；
- 保持 stdout 协议纯净，临时音频句柄不能绕过应用身份校验。

阶段门：主 Agent 可以完成“请求试听 → 查询任务 → 读取来源明确的结果”
闭环，且不具备任何隐式写入能力。

### 阶段 5：项目提示词和产品化收口

- 保存工程后按规则创建/读取音频子 Agent `AGENT.md`；
- 未保存工程显示提示但仍可使用系统提示词和主 Agent 提示词；
- 增加取消、过期、应用关闭、网络失败和模型能力不匹配的 UI 状态；
- 评估是否把音频句柄作为 Context Package 的可选证据；
- 在确定有实际价值前，不扩展为完整自主音乐 Agent。

## 验收标准

功能验收：

- 可以从钢琴卷帘试听并评审一个音色，默认使用 `C-5`；
- 可以从明确的 Pattern/Order/行范围导出并评审一个乐段；
- AI 确实以音频输入完成评审，音频能力不足会失败；
- 人工可以播放完全相同的音频并提交独立意见；
- 结果始终带有 `human` 或 `multimodal_ai` 来源及完整绑定信息；
- 音色清晰时可直接输出常见乐器名，困难时输出三维分类；
- 乐段存在明显问题时直接指出，否则覆盖四个约定维度；
- 文档修订变化后旧结果标记 stale，不能误用于当前乐谱；
- 任何试听结果都不能直接修改 Pattern 或触发 Apply。

工程验收：

- mock provider、原生渲染失败、范围错误、取消、断连、凭据缺失和能力不
  匹配都有自动化测试；
- AI 与人工使用同一音频哈希；
- 模型适配器可替换，MCP schema 不包含提供商专属分支；
- 未保存工程不会创建项目级 `AGENT.md`，但能够继续试听；
- 保存工程后只在首次需要时创建缺失文件，且不覆盖已有主 Agent 修改；
- 调试日志之外没有新增的项目级评审持久化数据；
- 现有 Pattern 编辑、播放、MCP Proposal/Apply 工作流不回归。

## 不在本计划内

- 让 AI 直接编辑 Pattern、自动 Apply 或替代人工 Proposal Review；
- 用音频模型结果替代 revision-bound Score Context；
- 首版强制生成完整 Context Package、Piano Roll 图片或全项目音频；
- 实现本地音频理解模型；
- 建设长期评审数据库、跨项目记忆或云端协作服务；
- 复制 OpenMPT 的播放/渲染实现到 Python；
- 因为加入试听能力而重做现有 MCP 连接、占用和 Proposal 生命周期。

## 待实现前确认的细节

这些问题不改变总体架构，但必须在对应阶段开始前落定：

1. 原生音色试听接口能否直接提供稳定的 PCM/WAV 捕获；
2. 音频范围导出的最小可复用接口及其对 Order 跳转、循环和 Pattern break
   的处理；
3. 首版统一音频格式、采样率、声道、最大时长和文件大小；
4. 当前部署环境中三个候选模型的实际 API 名、凭据配置和价格/配额；
5. 人工试听 UI 放置位置，以及人工提交者身份的最小表示；
6. 项目级音频子 Agent `AGENT.md` 的确切目录和创建时机；
7. 是否把可选的 Score Context、Piano Roll 图片和风格提示暴露给 AI 评审；
8. 任务结果在进程重启、文档关闭和 Sidecar 重连后的保留策略。

## 与现有 Wayfinder 决策的关系

- 复用 issue 02 的 OpenMPT 播放、渲染和文档能力，不扩大为全应用迁移；
- 遵守 issue 05 的 protocol-neutral Application Capability 边界；
- 遵守 issue 06、24、30、31 的本地 Sidecar、应用附着和 owning-thread 规则；
- 以 issue 07 的 revision-bound Score Context 为权威，音频评审只是可追溯
  的派生证据；
- 不改变 issue 20、23、25 已确定的 Proposal-first、人工 Apply、原子修改
  和普通 Undo 边界；
- 作为 issue 07 中被推迟的 Audio Preview/Mini Audio Reviewer 能力的独立
  落地方案，但不把它重新设为第一 AI Pattern 读写闭环的前置条件。
